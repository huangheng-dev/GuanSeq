# 业务切片：设备报警处置闭环 v1

> 状态：工程闭环完成，真实现场验收待完成  
> 日期：2026-08-26  
> 领域归属：`equipment`  
> 前置能力：设备台账、维修工单、Modbus/MQTT 只读采集、统一样本与技术预检

## 1. 业务目标

设备经理需要把采集值越限和通讯失败转成可追踪的报警责任，而不是只在当前值页面看到异常。报警必须保留触发、恢复、确认、处理、解决、关闭和维修关联证据，同时不得绕过设备与维修用例直接修改核心业务事实。

本切片使用现有模块化单体、PostgreSQL 与采集适配器完成闭环，不新增 Broker、消息中间件、时序数据库或独立告警服务。

## 2. 对象与数据所有权

| 对象 | 所有者 | 说明 |
|---|---|---|
| 报警规则 | `equipment` | 关联当前工作区的采集连接和可选点位，定义触发类型、阈值、级别与默认责任人 |
| 报警实例 | `equipment` | 同一规则当前未关闭的责任事实；保存条件状态与人工处置状态 |
| 报警事件 | `equipment` | 触发、再次触发、条件恢复和人工动作的不可变证据 |
| 维修工单 | `equipment` 既有用例 | 报警只可关联同设备的现有维修工单，不自动改变设备状态或创建/启动维修 |

## 3. 规则与触发

v1 支持三类规则：

- `HIGH_LIMIT`：数值大于等于上限；
- `LOW_LIMIT`：数值小于等于下限；
- `COMMUNICATION_FAILURE`：生产协议采集失败。

数值规则必须关联数值点位并配置阈值；通讯失败规则不得关联点位或阈值。规则状态为 `ACTIVE` 或 `PAUSED`，启停使用乐观锁并记录原因和请求编号。

同一规则同时最多存在一个未关闭报警。重复异常只更新末次发生时间和值，不为每个样本制造事件；条件恢复时写入一次 `CONDITION_CLEARED`。已恢复但尚未关闭的报警再次异常时重新打开并写入 `REOPENED`，防止重复报警和责任丢失。

## 4. 报警状态机

```text
OPEN -> ACKNOWLEDGED -> IN_PROGRESS -> RESOLVED -> CLOSED
  |           |              |
  +-----------+--------------+---- 条件恢复只写 conditionActive=false
```

- `ACKNOWLEDGE`：确认已看见，可更新责任人；
- `START_PROCESSING`：开始处置；
- `RESOLVE`：只有触发条件已经恢复时允许，必须填写解决说明；
- `CLOSE`：仅已解决报警可关闭；
- `LINK_REPAIR`：开放、已确认或处理中报警可关联同设备的未关闭维修工单，不改变两边状态。

报警保留独立的 `conditionActive`。采集恢复不会自动把报警改成“已解决”，人工也不能在条件仍存在时解决报警。

## 5. 权限、范围与审计

- 所有查询必须按租户和当前工作区过滤。
- `MAINTENANCE_MANAGER`、`PRODUCTION_MANAGER`、`ADMIN` 可以管理规则和处置报警；其他成员只读。
- 后端授权是唯一可信边界；前端隐藏按钮只用于体验。
- 规则创建/启停、报警触发/恢复、确认/处理/解决/关闭/维修关联均记录操作者（系统触发允许为空）、时间、来源、请求编号和前后状态。
- 报警事件只保存归一化值、质量和稳定错误码，不保存密码、主机、Topic 或 MQTT 原文。

## 6. 异常与恢复

- 样本重复或重复通讯失败不得生成重复报警实例。
- 规则、报警版本冲突返回 409，用户刷新后重试，不静默覆盖。
- 跨工作区连接、点位、报警或维修工单返回 404，不泄露存在性。
- 规则暂停后不评估新样本，但已有报警责任保留，必须继续处置或关闭。
- 报警评估失败不得直接修改设备业务状态；采集和报警均保留可追踪错误边界。

## 7. 验收条件

1. 数值越限与通讯失败均可通过生产采集链路生成报警。
2. 正常样本或通讯恢复将 `conditionActive` 置为 `false` 并保留恢复事件。
3. 重复异常不重复建单，恢复后再次异常可重新打开原未关闭报警。
4. 确认、处理、解决、关闭和维修关联状态机由后端强制执行。
5. 普通成员不能管理规则或处置报警，跨工作区访问被拒绝。
6. 页面覆盖加载、空数据、无权限、校验失败、接口失败、提交中和并发冲突。
7. Flyway、OpenAPI、PostgreSQL 集成测试、前端契约测试、lint、类型检查、生产构建与桌面/390px 浏览器流程通过。
8. 仿真触发只宣称工程闭环，不宣称真实工厂报警已经验收。

## 8. 非目标

- 不实现短信、邮件、企业微信等外部通知；
- 不实现厂商质量码报警；现有适配器没有可验证的厂商质量映射，不用值域警告伪装质量码；
- 不实现持续时间、迟滞、组合表达式、班次抑制或报警风暴策略；
- 不自动改变设备运行状态、自动创建维修工单或执行远程控制；
- 不承诺真实厂商阈值、现场网络、容量和值守升级机制已经验收；
- 不引入消息总线、规则引擎或独立告警服务。

## 9. 交付与验证结果

- V45 已建立报警规则、规则事件、报警实例和报警事件，并以“同一规则最多一个未关闭报警”的数据库约束守住责任唯一性。
- OpenAPI 已提供规则查询/创建/启停、报警查询/详情，以及确认、开始处理、解决、关闭和关联维修动作；前端 `/equipment/alerts` 通过同源 BFF 与运行时 Schema 接入。
- PostgreSQL/Testcontainers 集成测试已验证数值越限、通讯失败、条件恢复、重新打开、状态机、维修关联、权限、版本冲突与设备状态不被自动改变。
- 全量门禁通过：前端 lint、TypeScript、30 个测试文件/90 项测试和 Next.js 生产构建；后端 118/118 项测试、0 跳过和 Maven 生产打包，V1—V45 已在 PostgreSQL 18.4 空库完整执行。

- 以上只证明可替换工程闭环。真实阈值、质量码、网络、用户 Broker、容量、现场责任人与值守升级仍须现场验收。
