# GuanSeq 总体架构审计

> 审计对象：[系统总体架构与开发蓝图](./系统总体架构.md)  
> 审计日期：2026-08-14  
> 审计结论：通过，作为 GuanSeq 目标架构基线使用

## 1. 结论

这套架构不是通过堆叠技术来追求表面上的“顶级”，而是在 GuanSeq 的产品定位下追求最合适：制造事务稳定、业务事实清晰、现场可部署、物联网独立、AI 受控，并且能够从单工厂平滑演进到多工厂。

审计后的总体判断：

- **产品适配度：高**。覆盖 ERP、MES、WMS、QMS、PLM/PDM、APS、EAM 的事实边界，并以订单到交付为第一主闭环。
- **工程复杂度：合理**。核心选择模块化单体，没有过早采用 Spring Cloud 微服务。
- **长期扩展性：高**。领域模块、事件、数据所有权和独立 IoT/AI 服务为未来拆分保留了清晰接缝。
- **现场适应性：高**。考虑本地部署、边缘缓存、断网补传、PDA 和设备数据分层。
- **当前可执行性：高**。技术组件有明确职责，建设阶段和“不做什么”都清楚。

不存在脱离业务规模也绝对“最好”的架构。就 GuanSeq 面向普通制造企业、前端先行、后端后续建设的约束而言，这是一套成熟、克制且可实施的目标架构。

## 3. 第一轮发现与修订结果

### 3.1 批处理调度缺口

制造系统需要执行 MRP、成本结转、周期报表和定时检查。主文档已补充 Quartz 集群模式，第一阶段不额外部署独立调度平台。

### 3.2 报表读取可能影响交易性能

复杂经营分析不能直接压在订单和库存事务查询上。主文档已补充查询模型、物化视图、后台报表、读副本和按证据引入数据仓库的演进路径。

### 3.3 制造主数据版本规则不足

BOM、工艺路线、质量标准必须具备版本和生效时间。主文档已明确历史工单固定引用当时版本，并补充计量单位、精度和外部主数据映射规则。

### 3.4 消息顺序与重复消费

主文档已补充聚合 ID、聚合版本、稳定路由键、Inbox、Outbox、幂等和乱序处理要求。

### 3.5 现场离线边界

主文档已补充 PDA 低风险扫码任务的离线队列，并明确审核、付款和高风险库存调整不得离线执行。

### 3.6 软件供应链安全

主文档已增加 SBOM、依赖和容器镜像扫描要求，严重漏洞阻断发布。

## 4. 关键架构判断

### 4.1 为什么不直接使用 Spring Cloud

第一阶段的订单、库存、生产、质量和成本存在大量一致性关系。模块化单体可以使用本地事务保证关键事实一致，同时通过 Spring Modulith 约束模块边界。只有出现独立扩缩容、独立发布、团队自治或法规隔离证据后才拆分服务。

结论：当前不使用 Spring Cloud 是架构成熟度的表现，不是能力不足。

### 4.2 为什么选择 PostgreSQL

GuanSeq 需要复杂关联、批次与序列号追溯、历史分区、动态工艺/质量属性和多组织约束。PostgreSQL 可以同时满足强关系模型、JSONB、分区和扩展能力，并与 Spring Boot 生态兼容。

结论：PostgreSQL 是长期主库的合适选择；设备原始时序数据仍需独立存储。

### 4.3 为什么 RabbitMQ 和 MQTT 都需要

- RabbitMQ 传递订单、库存、质量和通知等业务事件。
- MQTT/EMQX 管理设备连接、状态、点位、报警和指令。

两者面对的连接模型、可靠性语义和消息生命周期不同。职责分开能够避免业务事件和设备流量互相干扰。

### 4.4 为什么 AI 独立部署

AI 模型迭代、算力、数据策略和失败方式与交易系统不同。独立 AI 服务通过受控工具 API 读取业务事实，不直接写库；高风险动作由人确认，因此模型失败不会破坏核心交易一致性。

## 5. 尚需在实施前定案的参数

以下不是架构缺陷，而是必须结合首批客户与真实负载确定的实施参数：

- 单租户独立部署、共享库多租户或混合模式。
- 核心业务与设备数据的 RPO、RTO 和保留周期。
- 首批工厂的设备协议、点位规模、采样频率和离线时长。
- 首批企业采用的 OIDC 身份提供者、声明映射与账号同步运营流程；协议与开发/正式身份互斥边界已由 ADR-0003 固化。
- 财务税务范围和是否对接现有财务软件。
- AI 使用云端模型、本地模型或混合模型的数据策略。
- 是否存在法规要求的电子签名、长期归档或数据驻留限制。

这些参数在首个后端迭代开始前通过 ADR 固化。

## 6. 架构风险与控制

| 风险 | 控制方式 |
|---|---|
| 模块化单体退化为大泥球 | Spring Modulith 边界验证、公开 API、模块测试、禁止跨模块写表 |
| PostgreSQL 被报表拖慢 | 读模型、物化视图、异步报表、读副本和数据生命周期 |
| RabbitMQ 造成最终一致性问题 | 模块内强事务、Outbox、幂等消费、补偿和人工重放 |
| 设备数据失控增长 | 采样死区、聚合、分区、保留与冷热分层 |
| 断网导致重复业务 | 边缘缓存、消息序列、幂等键和同步结果可见 |
| AI 幻觉或越权 | 权限继承、来源引用、评测集、工具白名单、人工确认和审计 |
| 多租户数据泄露 | 自动租户边界、后端授权、RLS 纵深保护和越权测试 |
| 技术栈过重 | 组件职责审查，未达到阈值不引入新中间件 |

## 7. 最终审计意见

该架构可以作为 GuanSeq 正式开发基线。它在“专业完整”和“不过度复杂”之间取得了正确平衡，也为 PostgreSQL、Spring Boot、MQTT、物联网和 AI 的后续建设给出了清晰边界。

后续必须坚持两点：

1. 不因为文档已经完整，就把规划能力当成已经实现。
2. 不因为未来可能拆微服务，就提前牺牲当前业务闭环的交付速度和事务一致性。
