# 业务切片：销售应收开票与收款核销

> 状态：已实现并通过真实 PostgreSQL 集成验证  
> 更新日期：2026-08-20

## 1. 业务目标

承接“销售发货与成品出库”产生的已发货数量，形成可追溯的应收发票和收款核销事实，使销售履约能够继续进入财务回款环节：

```text
销售订单已发货
→ 按订单行剩余已发数量开票
→ 形成客户应收余额与账期
→ 登记实际收款
→ 按具体发票核销
→ 部分收款或全部收清
```

## 2. 事实所有权与模块协作

- `sales` 拥有销售订单、客户/价格/税率快照和订单行累计已发数量。
- `finance` 拥有应收发票、发票行、收款、待收余额、核销状态和审计事件。
- 财务模块通过 `SalesReceivableQueryProvider` 读取销售模块公开的已发货快照，不访问销售表。
- 前端只调用业务 API，不直接读取数据库或拼装核心财务事实。

## 3. 状态与规则

应收发票状态：

```text
OPEN → PARTIALLY_PAID → PAID
```

核心约束：

- 仅 `PARTIALLY_SHIPPED` 或 `SHIPPED` 销售订单允许开票。
- 同一订单行累计开票数量不得超过累计已发数量。
- 支持分批开票；每张发票保留客户、订单、币种、税率、物料、单价与数量快照。
- 到期日不得早于开票日期。
- 收款日期不得早于开票日期，收款金额不得超过当前待收余额。
- 收款仅核销到一张明确的应收发票；跨发票自动分配不属于本切片。
- 写操作仅允许 `ADMIN`、`FINANCE_MANAGER`。
- 开票和收款均使用 `X-Request-Id` 幂等；收款同时校验发票乐观并发版本。
- 同一销售订单开票使用 PostgreSQL 事务级 advisory lock，防止并发超开。

## 4. API 与数据事实

正式契约位于 `guanseq-server/src/main/resources/openapi/guanseq-api-v1.yaml`：

- `GET /api/v1/finance/receivable-invoices`
- `GET /api/v1/finance/receivable-invoices/{id}`
- `GET /api/v1/finance/receivable-reference-data`
- `POST /api/v1/finance/receivable-invoices`
- `POST /api/v1/finance/receivable-invoices/{id}/receipts`

Flyway 事实来源：`V24__create_sales_receivable_invoices.sql`。

## 5. 前端入口

- `/finance/receivables`：应收余额、已收、待收、逾期与应收台账。
- `/finance/sales-settlement/invoicing`：可开票履约订单和开票动作。
- `/finance/sales-settlement/receipts`：未收清发票和收款核销动作。

三个入口共享同一业务数据，但按任务提供不同标题、说明和主要动作；表格提供搜索、状态筛选、排序、全选、导出、详情、首页/尾页和跳页。

## 6. 失败与并发语义

- 无权限：`403`。
- 发票版本或唯一请求冲突：`409`。
- 未发货、日期不合法、超开票或超收款：`422`。
- 前端 BFF 无法连接后端：明确提示服务不可用，不写入本地伪成功数据。
- 查询为空时展示可行动空状态；加载与接口失败沿用工作台统一边界。

## 7. 明确未实现

以下能力不属于本切片，界面和文档不得宣称已完成：

- 红字发票、作废、退款与反核销。
- 一笔收款跨多张发票的自动分配、预收款和未达账。
- 增值税发票平台、银企直联、银行流水自动对账。
- 总账凭证、会计期间、汇兑损益、坏账准备和信用控制。
- 采购应付、付款和基础三方数量校验已由独立切片交付；采购价差容差与暂估应付仍未实现。
