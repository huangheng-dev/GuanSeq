## 0. 设计立场（面向普通制造企业）

本切片按"普通制造企业财务实际操作"设计，不按大企业全套财务系统设计：

1. 红冲、反核销、退款**在一个切片内闭环**，不让用户在多个菜单间跳转才能完成一次退货退款。
2. 不引入独立的"退款单"业务对象——退款本质上就是一笔红字方向的收/付款，复用现有收款/付款表和编号逻辑，只增加方向字段。
3. 不做审批工作流、税务平台对接、银企直联、会计期间、总账凭证——这些属于后续切片，本切片只保证业务事实可审计。
4. 字段保留但不强制：增值税红字信息表编号对小规模纳税人可空；对一般纳税人在界面上提示填写。
5. 默认操作路径短：开具红字 → 若有应退余额则登记退款 → 结清，最多三步。

## 1. 业务目标

在不删除、不修改已过账发票与收付款事实的前提下，为销售应收和采购应付提供可审计的更正闭环：

```text
蓝字发票已过账
├─ 发票金额/数量有误
│   └─ 开具红字发票（按行或整票）
│       └─ 若已收款产生应退余额 → 登记退款 → 结清
└─ 收付款核销有误
    └─ 反核销该笔收款/付款 → 余额恢复 → 可重新核销
```

三类操作各自独立：

- **红字发票**：发票本身错了（退货、折让、单价错误）。
- **反核销**：钱记错了发票（串户、金额错误、银行退回）。
- **退款**：红字发票冲减后需要把钱实际退给客户或从供应商收回。退款是红字方向的收/付款，与正常收款/付款使用同一张表。

## 2. 事实所有权与模块协作

- `sales` 继续拥有销售订单、客户、订单行累计已发货数量；本切片不改变其事实。
- `procurement` 继续拥有采购订单、供应商、订单行累计合格收货数量；本切片不改变其事实。
- `finance` 拥有红字发票、红字发票行、反核销记录、退款记录、受影响后的应收/应付余额以及全部审计事件。
- 财务模块仍通过 `SalesReceivableQueryProvider` / `ProcurementPayableQueryProvider` 读取业务侧快照，不访问销售、采购、质量、仓储表。
- 红字发票过账后，财务模块对外提供的"累计已开票数量"查询必须把红冲数量扣减掉，使销售/采购侧看到的未开票余额恢复。

## 3. 红字发票

### 3.1 业务对象

红字发票是一张独立业务单据，引用一张已过账的蓝字发票：

- 红字发票有自己的编号、日期、到期日、币种、税率快照、金额快照。
- 红字发票行引用原蓝字发票行，记录红冲数量、红冲单价（默认取原行单价，允许覆写用于折让场景）。
- 红字发票净额、税额、含税金额均为**负数**，与蓝字发票在同一余额中自然累计。
- 红字发票编号使用独立序列，前缀 `ARCR-`（应收红字）/`APCR-`（应付红字），与蓝字发票编号不混排。
- `tax_notice_number` 字段保留增值税红字信息表编号，可空。

### 3.2 状态机

```text
DRAFT → POSTED
```

草稿可删除；过账后不可修改、不可删除，再有误需另开红字或蓝字更正。不设置 `CANCELLED` 状态，遵循"已过账事实不可变"。

### 3.3 核心规则

- 仅 `OPEN`、`PARTIALLY_PAID`、`PAID` 状态的蓝字发票允许开具红字发票。
- 同一蓝字发票行累计红冲数量不得超过该行累计已开票数量减去已红冲数量。
- 红冲单价必须 ≥ 0；红冲金额 = 红冲数量 × 红冲单价，税额按原发票税率计算。
- 红字发票到期日不得早于红字发票开票日期，红字开票日期不得早于原蓝字发票开票日期。
- 红冲原因非空，4–500 字符。
- 写操作仅允许 `ADMIN`、`FINANCE_MANAGER`。
- 开具红冲使用 `X-Request-Id` 幂等；同一原发票 + 同一请求编号不重复过账。
- 同一蓝字发票使用 PostgreSQL 事务级 advisory lock，防止并发红冲超额。

## 4. 退款（红字方向的收/付款）

### 4.1 业务对象

退款不新建独立表，而是在现有 `receivable_receipts` / `payable_payments` 上增加 `direction` 字段：

- `direction = 'RECEIPT'`（默认，现有数据）表示客户收款 / 向供应商付款。
- `direction = 'REFUND'` 表示向客户退款 / 从供应商收回退款。
- 退款记录的 `amount` 始终为正数（表示资金流动金额），通过 `direction` 区分方向；计算余额时退款冲减 `received_amount`/`paid_amount` 并扣减 `credit_balance`。
- 退款编号沿用各自序列，前缀 `ARRF-`（应收退款）/`APPF-`（应付退款），便于与正常收付款区分。

### 4.2 核心规则

- 退款只能针对存在 `credit_balance > 0` 的蓝字发票登记（即红冲后产生了应退余额）。
- 退款金额必须 > 0 且 ≤ 当前 `credit_balance`。
- 退款日期不得早于导致该余额的红字发票开票日期。
- 退款支付方式与正常收付款一致（银行转账、现金、票据、其他）。
- 退款过账后：
  - 发票 `credit_balance` 扣减退款金额。
  - 若 `credit_balance` 归零，发票状态从 `CREDIT_PENDING` 推进到 `SETTLED`（若正向仍有待收/待付余额则回到 `OPEN`/`PARTIALLY_PAID`）。
- 写操作仅允许 `ADMIN`、`FINANCE_MANAGER`。
- 退款使用 `X-Request-Id` 幂等，并校验发票乐观锁版本。
- 同一发票使用 advisory lock 串行化退款与红冲。

### 4.3 为什么不做独立退款单

对普通制造企业，退款就是"钱出去了/进来了"一个动作，不涉及审批流、采购退货单关联、多币种汇兑等复杂场景。独立退款单会带来：

- 用户需要在"红字发票"、"退款单"、"核销"三个菜单间切换；
- 表结构和状态机翻倍，测试和维护成本翻倍；
- 未来真有复杂退款场景（多发票合并退、预付款抵扣），再引入独立退款单切片也不迟。

本切片选择**复用收付款表 + direction 字段**，用最小结构覆盖 80% 场景。

## 5. 反核销

### 5.1 业务对象

反核销针对一笔已经过账的收款/付款（含退款），不针对发票本身：

- 反核销记录有独立编号 `ARRV-` / `APRV-`、反核销日期、原因、操作人。
- 反核销不删除原收付款记录，而是将其状态从 `POSTED` 改为 `REVERSED`，写入反向审计事件。
- 反核销后钱的实际去留由用户另行处理（重新登记正确的收付款，或再开退款），系统不自动判断。

### 5.2 状态机

```text
receipt/payment/refund: POSTED → REVERSED
```

`REVERSED` 为终态，不可再次反核销，不可撤销反核销。反核销录错时重新登记一笔正确的收付款。

### 5.3 核心规则

- 只有 `POSTED` 状态的收付款允许反核销。
- 反核销日期不得早于原收付款日期。
- 反核销必须填写原因（4–500 字符）。
- 反核销过账后，根据原记录的 `direction`：
  - `RECEIPT` 方向：原发票 `received_amount`/`paid_amount` 扣减，正向余额恢复，状态按剩余金额重算。
  - `REFUND` 方向：原发票 `credit_balance` 回补，状态回到 `CREDIT_PENDING`。
- 写操作仅允许 `ADMIN`、`FINANCE_MANAGER`。
- 反核销使用 `X-Request-Id` 幂等。
- 同一原发票使用 advisory lock 串行化反核销与新收付款/红冲。

## 6. 发票状态机（扩展后）

```text
OPEN ──收款──→ PARTIALLY_PAID ──收款──→ PAID
  ↑                │                       │
  └──反核销────────┴──────红冲─────────────┤
                                          ↓
                    红冲金额 > 已核销金额 → CREDIT_PENDING ──退款──→ SETTLED
                                          │
                    红冲金额 ≤ 待核销余额 → 回到 OPEN / PARTIALLY_PAID
```

- `OPEN`：有正向待收/待付余额。
- `PARTIALLY_PAID`：部分核销。
- `PAID`：正向余额已结清且无待退余额。
- `CREDIT_PENDING`：红冲后存在应退/应收回余额，等待退款。
- `SETTLED`：正向和反向余额均结清（含未收款直接红冲结清的情况）。

## 7. API 与数据事实

### 7.1 OpenAPI（已写入 `guanseq-api-v1.yaml`）

应收：

- `GET /api/v1/finance/receivable-credit-notes`：分页查询红字发票。
- `GET /api/v1/finance/receivable-credit-notes/{id}`：红字发票详情。
- `POST /api/v1/finance/receivable-credit-notes`：创建并过账红字发票。
- `POST /api/v1/finance/receivable-invoices/{id}/refunds`：登记退款。
- `POST /api/v1/finance/receivables/receipts/{id}/reverse`：反核销一笔收款或退款。

应付：

- `GET /api/v1/finance/payable-credit-notes`
- `GET /api/v1/finance/payable-credit-notes/{id}`
- `POST /api/v1/finance/payable-credit-notes`
- `POST /api/v1/finance/payable-invoices/{id}/refunds`
- `POST /api/v1/finance/payables/payments/{id}/reverse`

写接口接受 `X-Request-Id`：`409` 幂等/乐观锁冲突，`422` 业务校验失败，`403` 无权限，`404` 不存在。

### 7.2 Flyway `V28__create_credit_notes_reversal_and_refund.sql` 摘要

新增表（均在 `finance` schema）：

- `receivable_credit_notes` / `receivable_credit_note_lines`
- `payable_credit_notes` / `payable_credit_note_lines`
- `receivable_reversals` / `payable_reversals`

对现有表的变更：

- `receivable_invoices` / `payable_invoices`：
  - 状态 CHECK 扩展 `CREDIT_PENDING`、`SETTLED`；
  - 新增 `credit_balance NUMERIC(18,2) NOT NULL DEFAULT 0`。
- `receivable_receipts` / `payable_payments`：
  - 新增 `direction VARCHAR(16) NOT NULL DEFAULT 'RECEIPT'`，CHECK 为 `('RECEIPT','REFUND')`；
  - 状态 CHECK 扩展 `REVERSED`；
  - 新增 `reversal_id UUID`、`reversed_at TIMESTAMPTZ`、`credit_note_id UUID`（退款关联到导致余额的红字发票，可空以兼容历史数据）。
- 编号序列：`receivable_credit_note_number_seq`、`receivable_reversal_number_seq`、`payable_credit_note_number_seq`、`payable_reversal_number_seq`（退款复用现有 receipt/payment 序列）。
- `receivable_events` / `payable_events` 新增动作值：`CREATE_CREDIT_NOTE`、`POST_REFUND`、`REVERSE_RECEIPT`、`REVERSE_PAYMENT`。

所有新表含 `tenant_organization_id`、`workspace_id`、`request_id`、`version`、审计字段；金额一律 `NUMERIC`，不用浮点。

### 7.3 前端入口

- `/finance/receivables`：应收台账增加"红冲"行操作，红冲后若产生待退余额，详情抽屉内直接显示"登记退款"按钮。
- `/finance/receivables/receipts`：收款台账增加"反核销"行操作；退款以方向标签区分显示。
- `/finance/payables`：应付台账对称操作。
- `/finance/payables/payments`：付款台账对称操作。

红字发票过账弹窗必须显示：原发票号、累计已开、累计已冲、本次冲减后剩余、预计应退余额，二次确认后提交。退款弹窗必须显示：当前待退余额、本次退款后余额。

## 8. 失败与并发语义

- 无权限：`403`。
- 幂等冲突、乐观锁冲突、唯一请求编号冲突：`409`。
- 红冲数量超额、红冲日期非法、退款超额、反核销重复、原因缺失：`422`。
- 原发票/收款不存在或不在当前租户：`404`。
- 并发操作由 advisory lock 串行化；锁等待超时返回 `409`，提示刷新重试。
- BFF 无法连接后端时显示服务不可用，不写入本地伪成功数据。

## 9. 明确不在本切片

- 会计期间、关账、已关账期间禁止反核销（独立"会计期间与关账"切片）。
- 总账凭证、科目余额、汇兑损益、坏账准备、暂估应付。
- 增值税红字信息表自动申请、税务平台对接、银企直联。
- 预收/预付、多发票合并退款、预付款抵扣退款。
- 退货入库与红字发票的自动关联（当前红冲数量由人工确认，未来与销售退货/采购退货切片联动）。
- 审批工作流（沿用 `FINANCE_MANAGER` 角色直接过账；通用审批流平台上线后再接入）。
