## 1. 业务目标

在不删除、不修改已过账发票与收付款事实的前提下，为销售应收和采购应付提供可审计的更正手段：

```text
蓝字发票已过账
├─ 发票金额/数量有误  → 开具红字发票冲减（按行、按数量）
└─ 收付款核销有误    → 反核销该笔核销记录，恢复待核销余额
```

两类操作各自独立，可以单独使用：

- 红字发票针对的是"发票本身错了"（退货、折让、单价错误）。
- 反核销针对的是"钱记错了发票"（串户、金额错误、银行退回）。

红字发票与反核销都不允许物理删除或更新原凭证，全部以新增反向业务事实的方式表达。

## 2. 事实所有权与模块协作

- `sales` 继续拥有销售订单、客户、订单行累计已发货数量；本切片不改变其事实。
- `procurement` 继续拥有采购订单、供应商、订单行累计合格收货数量；本切片不改变其事实。
- `finance` 拥有红字发票、红字发票行、反核销记录、受影响后的应收/应付余额以及全部审计事件。
- 财务模块仍通过 `SalesReceivableQueryProvider` / `ProcurementPayableQueryProvider` 读取业务侧快照，不访问销售、采购、质量、仓储表。
- 红字发票过账后，财务模块对外提供的"累计已开票数量"查询必须把红冲数量扣减掉，使销售/采购侧看到的未开票余额恢复。

## 3. 红字发票

### 3.1 业务对象

红字发票是一张独立业务单据，引用一张已过账的蓝字发票：

- 红字发票有自己的编号、日期、到期日、币种、税率快照、金额快照。
- 红字发票行引用原蓝字发票行，记录红冲数量、红冲单价（默认取原行单价，允许覆写用于折让场景）。
- 红字发票净额、税额、含税金额均为**负数**（不是正数加方向字段），与蓝字发票在同一余额表中用正负方向自然累计。
- 红字发票编号使用独立序列，前缀 `ARCR-`（应收红字）/`APCR-`（应付红字），与蓝字发票编号不混排。

### 3.2 状态机

```text
DRAFT → POSTED
POSTED 不可删除、不可修改；如需再次更正，对红字发票再开蓝字或新的红字
```

红字发票不引入 `CANCELLED` 状态：草稿状态可直接废弃（删除草稿），过账后只能通过新单据更正。这与"已过账事实不可变"的原则一致。

### 3.3 核心规则

- 仅 `OPEN`、`PARTIALLY_PAID`、`PAID` 状态的蓝字发票允许开具红字发票。
- 同一蓝字发票行累计红冲数量不得超过该行累计已开票数量减去已红冲数量。
- 红冲单价必须 ≥ 0；红冲金额 = 红冲数量 × 红冲单价，税额按原发票税率计算。
- 红字发票到期日不得早于红字发票开票日期。
- 红字发票开票日期不得早于原蓝字发票开票日期。
- 若蓝字发票已部分或全部收款/付款：
  - 红冲过账后，原发票余额方向反转：应收红字部分形成对客户的待退余额，应付红字部分形成对供应商的待退余额。
  - 本切片不自动生成退款单；待退余额在原发票记录上以 `creditBalance` 字段暴露，由独立"收付款退款"切片消费。
- 若蓝字发票未收款/付款，红冲过账后直接减少应收/应付余额，对应释放销售/采购行的已开票数量。
- 写操作仅允许 `ADMIN`、`FINANCE_MANAGER`。
- 开具红冲使用 `X-Request-Id` 幂等；同一原发票 + 同一请求编号不重复过账。
- 同一蓝字发票使用 PostgreSQL 事务级 advisory lock，防止并发红冲超额。

### 3.4 对原发票状态的影响

应收原发票状态机在本切片后扩展为：

```text
OPEN → PARTIALLY_PAID → PAID
PAID/PARTIALLY_PAID ── 红冲金额 ≥ 已核销金额 ──→ OVERPAID（出现待退余额）
OPEN/PARTIALLY_PAID ── 红冲金额 < 待收余额 ──→ 回到 OPEN 或 PARTIALLY_PAID（按剩余待收重新计算）
```

`OVERPAID` 是新增状态，表示客户已付但红冲后存在应退余额；应付侧对称新增 `OVERPAID`（已超付，供应商应退）。退款单切片完成后，`OVERPAID` 随退款核销推进到结清状态。

## 4. 反核销

### 4.1 业务对象

反核销针对一笔已经过账的收款（应收）或付款（应付），不针对发票本身：

- 反核销记录有独立编号 `ARRV-` / `APRV-`、反核销日期、原因、操作人。
- 反核销不删除原收款/付款记录，而是将其状态从 `POSTED` 改为 `REVERSED`，并写入反向审计事件。
- 反核销不自动把钱退回客户/供应商银行账户；资金退回由独立退款单切片处理。

### 4.2 状态机

```text
receipt/payment: POSTED → REVERSED
```

`REVERSED` 为终态，不可再次反核销，也不可"撤销反核销"。若反核销本身录错，应重新登记一笔正确的收款/付款。

### 4.3 核心规则

- 只有状态为 `POSTED` 的收款/付款允许反核销；已被红冲联动影响的记录仍允许反核销。
- 反核销日期不得早于原收款/付款日期。
- 反核销必须填写原因（非空，长度 4–500 字符）。
- 反核销过账后：
  - 原发票 `receivedAmount` / `paidAmount` 扣减该笔金额。
  - 原发票状态按剩余金额重新计算（`OPEN` / `PARTIALLY_PAID` / `PAID`）；若因此回到 `OPEN`，允许继续登记新的收款/付款。
  - 若反核销时该发票已存在红字发票导致待退余额，状态仍按净余额计算，不允许借反核销绕开红字流程。
- 写操作仅允许 `ADMIN`、`FINANCE_MANAGER`。
- 反核销使用 `X-Request-Id` 幂等；同一原收款/付款 + 同一请求编号不重复反核销。
- 同一原发票使用事务级 advisory lock，防止反核销与新收款/红冲并发。

## 5. API 与数据事实

### 5.1 OpenAPI（新增路径，契约实现阶段写入 `guanseq-api-v1.yaml`）

应收：

- `GET /api/v1/finance/receivable-credit-notes`：分页查询红字发票。
- `GET /api/v1/finance/receivable-credit-notes/{id}`：红字发票详情，含原发票与红冲行。
- `POST /api/v1/finance/receivable-credit-notes`：创建并过账红字发票。
- `POST /api/v1/finance/receivables/receipts/{id}/reverse`：反核销一笔收款。

应付：

- `GET /api/v1/finance/payable-credit-notes`
- `GET /api/v1/finance/payable-credit-notes/{id}`
- `POST /api/v1/finance/payable-credit-notes`
- `POST /api/v1/finance/payables/payments/{id}/reverse`

写接口均接受 `X-Request-Id`，返回 `409` 表示幂等冲突或乐观锁冲突，`422` 表示业务校验失败，`403` 表示无权限。

### 5.2 Flyway `V28__create_credit_notes_and_reversal.sql` 摘要

新增表（均在 `finance` schema）：

- `receivable_credit_notes` / `receivable_credit_note_lines`
- `payable_credit_notes` / `payable_credit_note_lines`
- `receivable_reversals` / `payable_reversals`

对现有表的变更：

- `receivable_invoices.status` 检查约束扩展 `OVERPAID`；新增 `credit_balance NUMERIC(18,2) NOT NULL DEFAULT 0`。
- `payable_invoices.status` 检查约束扩展 `OVERPAID`；新增 `credit_balance NUMERIC(18,2) NOT NULL DEFAULT 0`。
- `receivable_receipts.status` 检查约束扩展 `REVERSED`；新增 `reversed_at TIMESTAMPTZ`、`reversal_id UUID`。
- `payable_payments.status` 检查约束扩展 `REVERSED`；新增 `reversed_at TIMESTAMPTZ`、`reversal_id UUID`。
- 新增编号序列：`receivable_credit_note_number_seq`、`receivable_reversal_number_seq`、`payable_credit_note_number_seq`、`payable_reversal_number_seq`。
- `receivable_events.action` / `payable_events.action` 已有 VARCHAR(40)，新增动作值：`CREATE_CREDIT_NOTE`、`REVERSE_RECEIPT`、`REVERSE_PAYMENT`。

所有新增表包含 `tenant_organization_id`、`workspace_id`、`request_id`、`version`、`created_by/at`、`updated_by/at`，数量金额使用 `NUMERIC`，不使用浮点。

## 6. 失败与并发语义

- 无权限：`403`。
- 幂等冲突、乐观锁冲突、唯一请求编号冲突：`409`。
- 红冲数量超额、红冲日期非法、反核销重复、原因缺失：`422`。
- 原发票/收款不存在或不在当前租户：`404`。
- 并发红冲/反核销由 advisory lock 串行化；锁等待超时返回 `409`，提示刷新后重试。
- BFF 无法连接后端时显示服务不可用，不在本地写入伪成功数据。

## 7. 明确不在本切片

- 客户退款单、供应商退款付款单及其与红字发票的自动核销（独立"收付款退款"切片）。
- 会计期间、关账、已关账期间禁止反核销（独立"会计期间与关账"切片）。
- 总账凭证、科目余额、汇兑损益、坏账准备。
- 增值税红字信息表自动申请、税务平台对接、银企直联。
- 预收/预付、暂估应付、采购价差容差审批、运杂费分摊。
- 红字发票的审批工作流（当前沿用 `FINANCE_MANAGER` 角色直接过账；通用审批流平台上线后再接入）。
