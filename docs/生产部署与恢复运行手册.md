# GuanSeq 生产部署与恢复运行手册

> 状态：开源生产部署工程基线  
> 适用范围：单实例、单工厂或受控试点  
> 事实边界：本手册证明发行物可重复部署和恢复，不证明任何客户实例已经上线

## 1. 运行单元与责任

生产 Compose 只包含：

```text
外部 HTTPS 入口
  → guanseq-web（唯一宿主入口，默认 127.0.0.1:3000）
    → guanseq-server（仅 Compose 内部网络）
      → PostgreSQL（唯一核心业务数据库，仅 Compose 内部网络）
```

部署负责人拥有镜像、Compose、TLS 入口和应用配置；数据库负责人拥有备份、恢复、保留与 RPO/RTO；身份负责人拥有 OIDC 客户端、回调、受众和密钥。业务数据仍由 GuanSeq Server 受控业务 API 写入，Compose、Web、反向代理和备份脚本不得修改业务事实。

本基线没有引入 Redis、RabbitMQ、EMQX、MinIO、Kubernetes、Prometheus 或 OpenTelemetry 后端。单机 Compose 不是高可用方案；多副本、WAL 连续归档、集中指标与链路平台必须根据安装环境另行验收。

## 2. 前置条件

- 受支持的 Linux Docker 主机或等价受控 OCI 环境，Docker Engine 与 Compose v2 可用。
- 已有 HTTPS 反向代理、负载均衡器或云入口；证书、TLS 策略和防火墙由安装环境负责。
- 正式 OIDC 保密客户端、公开 JWK、受众和固定回调已登记。
- 受控 PostgreSQL 卷和独立备份存储；备份存储需要加密、访问控制和异机副本。
- 明确部署、身份、数据库和业务责任人，并写明 RPO、RTO、保留周期和维护窗口。
- 不在仓库目录、镜像、工单正文或日志中保存真实密钥。

## 3. 生产配置预检

把 [.env.production.example](../.env.production.example) 复制到仓库外的受控路径，例如 `/etc/guanseq/production.env`，权限设为仅部署账号可读。逐项替换示例值后运行：

```bash
pnpm production:preflight -- --env-file /etc/guanseq/production.env
pnpm pilot:preflight -- --env-file /etc/guanseq/production.env
```

第一条离线检查语义版本、OIDC/TLS 回调、密钥独立性、数据库标识、备份 RPO/RTO 及 Compose 解析；第二条从受控网络检查 OIDC discovery、授权码/PKCE 和公开签名密钥。任何 `[FAIL]` 都阻止部署；`[WARN]` 必须由对应责任人记录接受理由。

预检不会打印密钥。`GUANSEQ_BOOTSTRAP_ENABLED=true` 只允许空正式库首次初始化窗口使用，初始化完成后必须恢复 `false` 并从密钥系统删除令牌。

## 4. 构建与启动

构建同一版本的两个非 root 镜像：

```bash
docker compose --env-file /etc/guanseq/production.env -f compose.production.yaml build --pull
```

发布前记录源提交、`GUANSEQ_VERSION`、两个镜像摘要、当前 Flyway 版本和部署前备份标识。确认后启动：

```bash
docker compose --env-file /etc/guanseq/production.env -f compose.production.yaml up -d --wait
docker compose --env-file /etc/guanseq/production.env -f compose.production.yaml ps
```

PostgreSQL 先健康，后端再执行 Flyway 并通过 `/api/v1/platform/status`，最后 Web 的 `/api/health` 真实探测后端。数据库和后端没有宿主端口；Web 默认只绑定 `127.0.0.1`。两个应用容器使用非 root、只读根文件系统、临时目录、全部 capability 删除和 `no-new-privileges`；PostgreSQL 使用官方镜像的权限切换与数据卷模型，不把应用容器约束误套到数据库初始化入口。

## 5. 外部反向代理与 TLS

正式域名只能通过 HTTPS 入口访问。GuanSeq 不强制安装某个代理产品；如果安装环境已有 Nginx，可参考下列边界并按组织安全基线补充证书、限流、WAF 和日志策略：

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_buffering off;
    client_max_body_size 16m;
    proxy_read_timeout 60s;
}
```

不要把 3000、8080 或 5432 直接开放给非受控公网。若必须把 Web 绑定为 `0.0.0.0`，预检要求显式确认 TLS 终止，并由防火墙只允许受控代理来源。OIDC 回调和退出回调必须与 `GUANSEQ_PUBLIC_ORIGIN` 同源。

## 6. 上线后验收与可观测边界

首先检查：

```bash
curl --fail --silent https://<正式域名>/api/health
docker compose --env-file /etc/guanseq/production.env -f compose.production.yaml logs --since 15m web server
```

健康响应只能包含服务、状态和版本，不能包含密钥或业务数据。后端日志带 `requestId`，BFF 与业务 API 通过 `X-Request-Id` 关联。上线窗口至少观察容器重启、健康状态、HTTP 错误、OIDC 失败、接口延迟、数据库连接/锁、Flyway 和磁盘容量，并为每项设置负责人、阈值和升级路径。

当前基线只提供健康、版本、容器状态和请求编号日志，不宣称已经交付完整指标、分布式追踪或集中告警平台。安装者可把 stdout/stderr 与健康端点接入已有观测平台；若项目未来内置新的采集组件，必须另建 ADR。

真实登录、成员权限、十三项只读 API 以及制造主闭环继续按[试点上线运行手册](./试点上线运行手册.md)验收。

## 7. 备份与隔离恢复演练

PostgreSQL 容器健康后生成 custom format 备份：

```bash
pnpm production:backup -- --env-file /etc/guanseq/production.env
```

脚本同时生成 `.dump` 和 `.manifest.json`，清单包含 SHA-256、字节数、应用版本和成功 Flyway 迁移数量。脚本不会自动删除旧备份；数据库负责人按保留策略在外部备份系统处理生命周期，避免误删唯一副本。

每个候选版本和每个正式备份策略至少执行一次隔离恢复演练：

```bash
pnpm production:restore-drill -- --env-file /etc/guanseq/production.env --backup /secure/backups/guanseq-<时间>.dump
```

恢复脚本先验证文件名、长度和 SHA-256，再创建随机命名的隔离数据库，执行 `pg_restore --exit-on-error`，核对 Flyway 数量，最后删除演练数据库。它不会停止应用、切换连接或覆盖原数据库。演练结果、耗时、备份标识和责任人应进入发布证据。

正式恢复采用：停止写入 → 保留故障证据 → 恢复到新数据库 → 校验迁移与只读业务事实 → 修改受控数据库连接 → 启动验证。禁止自动 `--clean` 覆盖原库、删除 Flyway 记录或手工逆向迁移。

## 8. 升级与回退

升级顺序：

1. 通过前后端、镜像安全和生产预检门禁。
2. 停止高风险写入并完成可恢复备份及隔离恢复演练。
3. 记录旧镜像摘要、版本、Flyway 和回退负责人。
4. 拉取或构建明确版本，禁止使用 `latest`。
5. 执行 `docker compose ... up -d --wait`，核对 Flyway、健康、登录和只读冒烟。
6. 逐步恢复写入并观察约定窗口。

应用回退和数据恢复是两件事：

- 若新版本未产生业务写入且迁移保持旧应用兼容，可把镜像版本改回已记录摘要，数据库保留前向版本。
- 若新迁移不兼容旧应用，不能直接启动旧镜像；停止写入并选择前向修复。
- 只有尚未产生正式写入、且部署前备份已验证时，才可恢复到新数据库并切换连接。
- 已产生正式业务写入后禁止用旧备份覆盖；保留证据并实施受控前向修复或数据更正。

## 9. 关闭与数据保留

停止应用但保留数据库卷：

```bash
docker compose --env-file /etc/guanseq/production.env -f compose.production.yaml down
```

不要使用 `down -v`，除非这是经过审批、已经验证备份且明确销毁数据的退役操作。普通升级、故障处理和回退都不得删除生产卷。

## 10. 完成标准

- 生产预检和 OIDC 网络预检无失败。
- 两个镜像以同一明确版本构建，非 root、安全默认值和健康检查生效。
- Compose 三服务健康，数据库/后端未暴露，HTTPS 入口和转发头正确。
- SBOM 已生成，源码与镜像 HIGH/CRITICAL 门禁通过或有到期例外记录。
- 备份清单、隔离恢复演练、实测 RPO/RTO 和异机副本均有证据。
- 真实登录、权限允许/拒绝、只读冒烟与受控业务闭环通过。
- 已知限制、观测责任、升级窗口和回退决定已记录。

只有工程项完成可称为“开源生产部署基线可用”；只有具体安装实例完成外部 TLS、OIDC、备份、观测和业务证据验收，才可称该实例生产上线。
