# GuanSeq 开发规范与交付流程

> 文档状态：强制执行  
> 生效日期：2026-08-14  
> 适用范围：产品、前端、后端、数据库、测试、集成、AI、物联网与运维  
> 目标：让人工与 AI 编程都以同一业务事实、工程边界和交付门禁工作

## 1. 核心原则

1. **业务闭环优先**：先完成一个能够真实流转、追踪和恢复的业务切片，再扩展页面或模块。
2. **事实只有一个来源**：数据库结构、API、产品范围和架构决策分别由明确文档或契约管理。
3. **最小充分架构**：只引入当前业务确实需要的技术，不为未来假设提前增加基础设施。
4. **后端守住业务边界**：权限、状态机、金额、库存、成本、审计和并发规则不能只存在于前端。
5. **规划不冒充交付**：Mock、规划能力、外部依赖和未接入能力必须明确标识。
6. **可验证才算完成**：代码存在、页面可见或接口返回 200 都不等于业务完成。

## 2. 事实来源与优先级

| 内容 | 事实来源 | 说明 |
|---|---|---|
| 强制工程规则 | `AGENTS.md` | 所有开发任务首先遵守 |
| 产品范围与业务闭环 | `docs/产品与前端架构.md`、业务需求 | 定义做什么和不做什么 |
| 目标技术架构 | `docs/系统总体架构.md` | 描述长期方向，不代表全部立即部署 |
| 重大技术决策 | `docs/adr/*.md` | 与通用蓝图冲突时，以已接受且更新的 ADR 为准 |
| 数据库结构 | Flyway 迁移脚本 | 不以 ORM 自动建表或口头说明为准 |
| HTTP API | OpenAPI 契约 | 前后端共同契约 |
| 前端服务边界 | `src/services` | 页面不得自行拼接接口或读取散落 Mock |
| 交付状态 | 自动化检查、验收证据 | 不以开发者主观判断为准 |

发现文档与代码不一致时，必须先确认真实状态并修正文档，不得默默选择方便的一方。

## 3. 默认架构基线

当前默认运行单元保持最少：

```text
guanseq-web
    → REST / OpenAPI
guanseq-server（Spring Boot 模块化单体）
    → PostgreSQL
```

默认允许的基础技术：

- 前端：现有 Next.js、React、TypeScript 工程。
- 后端：Java LTS、Spring Boot、Spring Modulith、Spring Security。
- 数据：PostgreSQL、Flyway。
- 契约：OpenAPI、Zod/生成客户端边界。
- 测试：单元测试、真实 PostgreSQL 容器集成测试、契约测试和关键流程测试。

架构清单只记录已经批准并进入实施范围的组件。尚未采用的技术不作为“候选占位”写入当前架构；未来出现新需求时，按第 11 节单独决策。

## 4. 工作项进入开发前的准备条件

一个工作项至少明确以下内容才进入实现：

- 解决哪个岗位的什么业务问题。
- 业务对象及其唯一责任模块。
- 初始状态、允许动作、目标状态和禁止动作。
- 操作人、数据范围与敏感字段权限。
- 上游输入、下游输出和关联单据。
- 正常路径、异常路径、撤销/冲销/重试或人工恢复方式。
- 可观察、可测试的验收条件。
- 明确不在本次范围内的内容。

信息不足但不影响安全和架构时，可以作出最小假设并记录；会改变业务事实、权限、资金、库存或技术架构时，必须先确认。

## 5. 标准开发流程

### 5.1 任务理解与现状检查

1. 阅读 `AGENTS.md`、本规范、相关产品文档和已接受 ADR。
2. 检查现有路由、组件、服务、数据库迁移、API 契约和测试。
3. 检查工作区状态，识别用户未提交改动，避免覆盖或扩大修改范围。
4. 写出业务目标、非目标、风险和可验证验收条件。

### 5.2 业务设计

1. 确定领域归属和数据所有者。
2. 定义状态机、命令、查询、事件和业务不变量。
3. 明确权限、数据范围、审批、审计和并发处理。
4. 明确失败后的恢复方式，禁止只设计成功路径。

推荐用下列结构描述关键对象：

```text
专业列表
→ 专业详情
→ 受控表单
→ 业务状态机
→ 权限与审批
→ 关联单据
→ 操作证据
→ 异常与恢复
```

### 5.3 数据与契约设计

1. 使用 Flyway 创建向前兼容的数据库迁移。
2. 定义 OpenAPI 请求、响应、错误、分页、排序和筛选契约。
3. 明确技术主键与可读业务编号，禁止用可变业务字段充当数据库主键。
4. 金额和数量使用精确数值类型，不使用浮点数保存业务金额。
5. 时间、时区、单位、币种和精度必须在契约中明确。
6. 可编辑聚合按风险使用版本号或其他并发控制，不能静默覆盖他人修改。

### 5.4 后端实现

每个业务模块内部采用：

```text
module
├─ api             对其他模块公开的命令、查询和事件
├─ application     用例编排、事务、权限和幂等
├─ domain          聚合、规则、值对象和领域服务
└─ infrastructure  PostgreSQL、消息和外部适配器
```

实现要求：

- 控制器只处理协议适配、输入校验和响应映射，不承载领域规则。
- 应用层负责用例、事务边界、权限和幂等。
- 领域层不依赖 Web、数据库、消息或第三方 SDK。
- 模块只能通过公开 API 或已定义事件协作。
- 一个模块不得直接查询或更新另一个模块拥有的表。
- 外部系统通过适配器接入，失败、超时和重试策略必须明确。
- 领域事件不是默认方案；本地直接调用更清晰时，不强行异步化。

### 5.5 前端接入

1. 页面继续通过 `src/services` 访问业务数据。
2. 用正式 API Adapter 替换对应 Mock Adapter，不让页面感知后端地址。
3. 优先使用 OpenAPI 生成客户端或受控契约映射，避免手写重复类型。
4. 服务端分页、排序、筛选和权限成为正式事实后，移除对应前端伪逻辑。
5. 页面必须覆盖加载、刷新、空数据、无权限、校验失败、接口失败、网络中断和提交中状态。
6. 审核、反审核、作废、冲销、删除等动作必须展示真实业务后果与确认信息。

### 5.6 验证与验收

按风险选择并执行：

- 领域单元测试：业务不变量、状态机、金额、数量和日期规则。
- 模块边界测试：无循环依赖、无跨模块基础设施访问。
- PostgreSQL 集成测试：迁移、约束、查询、并发和事务行为；关键 SQL 不使用 H2 代替。
- API 契约测试：成功、校验错误、无权限、冲突和不存在。
- 权限测试：功能权限、数据范围、字段权限和越权访问。
- 前端测试：服务适配、关键状态和回归门禁。
- 浏览器验收：桌面与目标移动断点的完整任务流程。
- 生产构建：lint、类型检查、自动化测试和构建全部通过。

验证失败必须修复或明确标为阻塞；不得通过删除测试、降低断言或隐藏错误完成交付。

### 5.7 交付与记录

1. 更新相关产品、架构、API 和运维文档。
2. 数据库变更、配置项和部署影响必须写入交付说明。
3. 记录已验证内容、未验证内容、已知限制和下一步。
4. 提交保持单一意图，不夹带无关格式化或重构。
5. 重大架构变化必须引用对应 ADR。

## 6. 数据库规范

- PostgreSQL 是核心业务事实库；浏览器、AI、报表和外部系统不得直接写库。
- 所有结构变化必须通过 Flyway，禁止依赖 ORM 自动修改生产结构。
- 迁移一经进入共享环境不得改写历史文件；通过新迁移修正。
- 删除列、改类型和大规模回填使用扩展—迁移—收缩策略，保证滚动升级兼容。
- 表、索引、唯一约束、外键和检查约束必须服务于明确业务不变量。
- 核心记录至少保留创建人、创建时间、最后修改人、最后修改时间和并发版本等适用证据。
- 软删除、状态关闭和不可篡改账本按业务含义选择，禁止所有表机械套用软删除。
- 日志和异常信息不得包含密码、令牌、密钥或不必要的敏感业务数据。

## 7. API 与错误规范

- API 采用明确版本边界，契约先行并保持向后兼容。
- 不直接暴露 ORM 实体；请求、响应和领域对象各自承担明确职责。
- 列表统一支持服务端分页，并按页面需要支持排序、筛选和总数。
- 错误响应至少包含稳定错误码、用户可理解信息、请求编号和可选字段错误。
- 业务冲突与系统故障必须区分，禁止全部返回成功或统一返回 500。
- 创建、审核、过账、库存移动等高风险命令按需要提供幂等机制。
- 每个请求具备可追踪请求编号，并贯穿日志、审计和异步任务。

## 8. 权限、安全与审计

- 后端默认拒绝，按用户、组织、工作区、角色和数据范围授权。
- 多组织与多工厂边界必须进入查询条件和写入校验，不能只依赖前端传参。
- 前端隐藏入口只是体验优化，不是安全措施。
- 高风险动作必须记录操作者、对象、动作、前后状态、时间、来源和请求编号。
- AI 只能使用不高于当前用户的数据权限，不直接写核心数据库。
- 密钥通过环境或密钥管理注入，不进入代码、仓库、截图和日志。

## 9. 测试分层与最低门禁

每次交付至少满足：

```text
格式与静态检查
→ 类型检查
→ 单元测试
→ 受影响模块集成测试
→ 契约/权限测试
→ 关键流程验收
→ 生产构建
```

缺陷修复必须先定位根因，并增加能够在修复前失败、修复后通过的回归测试。纯视觉问题无法稳定自动化时，应保留对应视口的视觉证据和人工验收项。

## 10. Git 与变更管理

- 开始任务前检查工作区，禁止覆盖、重置或删除不属于本任务的改动。
- 提交按业务意图拆分，提交说明描述“为什么”和业务结果。
- 不提交构建产物、运行日志、密钥、本地数据库和临时截图。
- 禁止使用破坏性历史重写处理普通开发问题。
- 数据库迁移、公共 API 和权限模型变更必须在评审中显式标注。
- 发布前建立可回滚版本点，并确认迁移的前向恢复方案。

## 11. 技术引入门禁

新增框架、中间件、数据库、独立服务或部署组件前，必须同时满足：

1. 有当前业务或非功能问题的可复现证据。
2. 已证明当前架构不能以合理成本解决该问题。
3. 明确开发、部署、监控、备份、安全和升级成本。
4. 定义成功指标、失败退出条件和替换路径。
5. 创建并接受 ADR。

“行业都在用”“以后可能需要”“显得更专业”均不是有效证据。

## 12. 完成标准（Definition of Done）

一个工作项只有同时满足适用条目才算完成：

- [ ] 验收条件与非目标明确。
- [ ] 领域归属、状态机和业务不变量明确。
- [ ] 权限、数据范围、审计和异常恢复已经实现。
- [ ] 数据库迁移可重复执行并经过真实 PostgreSQL 验证。
- [ ] OpenAPI 契约与实现一致。
- [ ] 前端通过 `src/services` 接入，不包含临时直连或重复契约。
- [ ] 加载、空数据、失败、无权限、提交中和冲突状态已经覆盖。
- [ ] 单元、集成、契约、权限和回归测试按风险完成。
- [ ] lint、类型检查、测试和生产构建全部通过。
- [ ] 关键桌面与移动任务流程完成验收。
- [ ] 文档、配置和部署说明同步更新。
- [ ] 没有把 Mock、规划或未接入能力描述为正式交付。
- [ ] 没有引入未经 ADR 证明必要的新技术。

未满足的条目必须在交付说明中明确列为限制或阻塞，不得省略。

## 13. AI 编程执行约定

AI 在 GuanSeq 中执行任务时必须：

1. 先读取约束和相关事实来源，再修改文件。
2. 以当前代码和可运行结果为证据，不凭记忆假设框架行为。
3. 优先复用现有组件、服务、契约和领域模式。
4. 不擅自扩大范围，不顺手加入技术、不相关页面或大规模重构。
5. 对可逆的小决策采用最小合理假设；对权限、资金、库存、架构和破坏性操作先确认。
6. 修改后自行完成与风险相称的验证，并报告实际结果。
7. 清楚区分“已实现、已验证、已规划、未验证和受阻”。

本规范本身发生重大变化时，也必须通过 ADR 或明确的产品决策记录原因。
