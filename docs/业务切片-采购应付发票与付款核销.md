# 业务切片：采购应付发票与付款核销

> 状态：已实现并通过真实 PostgreSQL 集成验证  
> 更新日期：2026-08-20

## 1. 业务目标

承接采购订单、收货和来料检验形成的合格入库数量，建立可追溯的供应商应付与付款事实：

```text
采购订单已下达
→ 到货收货
→ 免检入库或 IQC 结算
→ 按订单行合格收货数量登记供应商发票
→ 形成应付余额与账期
→ 登记实际付款并核销
→ 部分付款或全部付清
```

## 2. 事实所有权与模块协作

- `procurement` 拥有供应商、采购订单、订单行和累计合格入库数量。
- `quality` 与 `warehouse` 分别拥有来料检验判定及库存流水证据；采购模块只在检验结算后累计合格数量。
- `finance` 拥有应付发票、发票行、付款、待付余额、核销状态和审计事件。
- 财务模块通过 `ProcurementPayableQueryProvider` 读取采购模块公开的合格收货快照，不访问采购、质量或仓储表。

## 3. 状态与业务规则

应付发票状态：

```text
OPEN → PARTIALLY_PAID → PAID
```

核心约束：

- 采购订单行必须存在合格收货数量才能登记应付发票；待检和不合格数量不能开票。
- 同一采购订单行累计开票数量不得超过累计合格收货数量，支持分批收货和分批开票。
- 每张发票保留供应商、采购订单、币种、税率、物料、单价、数量和供应商发票号快照。
- 同一租户、同一供应商的供应商发票号不得重复。
- 到期日不得早于发票日期；付款日期不得早于发票日期。
- 付款金额不得超过当前待付余额；每笔付款核销到一张明确的应付发票。
- 写操作仅允许 `ADMIN`、`FINANCE_MANAGER`。
- 发票和付款命令使用 `X-Request-Id` 幂等；付款校验发票乐观并发版本。
- 同一采购订单及同一供应商发票号使用 PostgreSQL 事务级 advisory lock，防止并发超开或重复登记。

## 4. API 与数据库事实

OpenAPI 契约：`guanseq-server/src/main/resources/openapi/guanseq-api-v1.yaml`。

- `GET /api/v1/finance/payable-invoices`
- `GET /api/v1/finance/payable-invoices/{id}`
- `GET /api/v1/finance/payable-reference-data`
- `POST /api/v1/finance/payable-invoices`
- `POST /api/v1/finance/payable-invoices/{id}/payments`

Flyway 事实来源：`V25__create_purchase_payable_invoices.sql`。

## 5. 失败与恢复语义

- 无权限：`403`。
- 发票版本、请求编号或供应商发票号冲突：`409`。
- 无合格收货、日期不合法、超量开票或超额付款：`422`。
- 重复请求返回原业务结果，不重复生成发票、付款或审计事件。
- 并发冲突由调用方刷新最新版本后人工确认并重试，不静默覆盖。

## 6. 明确未实现

- 发票作废（蓝字发票已过账后不可直接作废，需通过红字发票更正）。
- 一笔付款跨多张发票自动分配、预付款、未达账和银企直联。
- 采购价差容差审批、运杂费分摊和暂估应付。
- 税务平台、总账凭证、会计期间、汇兑损益与关账。
- 红字冲销、退款和反核销已由[红字发票与反核销切片](./业务切片-红字发票与反核销.md)交付。

这些能力必须以后续独立切片交付，不得从当前正向闭环推断为已完成。

## 7. 验收证据

- Flyway 在一次性 PostgreSQL 18.4 容器中从空库迁移至 V25。
- OpenAPI 契约测试覆盖新增路径与 Schema。
- PostgreSQL 集成测试覆盖合格收货开票、金额计算、参考数据、请求幂等、部分/全部付款。
- 失败路径覆盖超量开票、重复供应商发票号、超额付款、旧版本和无权限写入。
- 完整交付门禁以 `guanseq-server` 的 `mvnw verify` 结果为准。
