# ADR-0003：OIDC 正式身份接入

- 状态：接受
- 日期：2026-08-24
- 决策人：GuanSeq 产品负责人、Codex
- 关联需求/问题：本地开发身份不能作为试点或生产认证边界，需要建立可替换、可验证且不绕过贯序内部权限事实的正式身份链路
- 取代：无
- 被取代：无

## 背景与问题证据

当前后端只提供一个进程内 Basic 用户，前端在本地环境把固定用户名和密码拼入每次 BFF 请求。关闭该适配器后，系统会安全地拒绝请求，但还没有完成登录入口、令牌校验、浏览器会话保护或外部身份与内部用户的映射，因此无法进入真实试点。

贯序现有的用户、工作区、成员关系、角色与审计事实已经位于 `identity` 模块。外部身份提供者只能证明“来访者是谁”，不能替代内部账号启停、工作区成员关系和业务授权。若直接信任外部角色、把访问令牌暴露给浏览器脚本，或由前端传入用户名，会破坏现有权限与审计边界。

## 决策驱动因素

- 采用制造企业常见身份提供者均能支持的开放协议，避免绑定具体供应商；
- 浏览器脚本不得读取访问令牌、客户端密钥或登录流程临时凭据；
- 后端必须独立验证签名、签发者、受众和有效期，不能信任 BFF 注入的用户名；
- 外部身份必须精确映射到贯序内部启用用户，且不得自动创建账号或接受外部角色作为业务权限；
- 本地开发应保持低门槛，但开发身份和正式身份必须互斥、显式启用；
- 认证失败仍使用统一 JSON 错误和请求编号，并能通过自动化测试验证。

## 候选方案

### 方案 A：继续使用 Basic 或反向代理注入用户名

改动较小，但固定密码不适合正式环境；代理头依赖网络拓扑和额外信任配置，后端无法独立验证来访者身份，也不具备标准登录与退出语义。

### 方案 B：Next.js 与 Spring Boot 共同采用 OIDC/JWT

Next.js 作为 BFF 执行 OIDC 授权码流程和 PKCE，将短期访问令牌保存在加密、HttpOnly、SameSite 会话 Cookie 中；Spring Boot 作为 OAuth 2.0 Resource Server 独立验证 Bearer JWT。协议标准、供应商可替换，且与现有 BFF 和模块化单体边界一致，但会新增标准协议库、密钥配置和令牌生命周期维护成本。

### 方案 C：由 Spring Boot 建立服务器会话并让前端直接持有会话 Cookie

可以集中认证逻辑，但会把浏览器跨源 Cookie、CSRF、会话存储和横向扩展问题引入当前无状态 API，同时削弱 Next.js BFF 的边界。

## 决策

选择方案 B：

- 正式环境使用 OpenID Connect 授权码流程和 PKCE；Next.js BFF 是保密客户端，负责登录、回调、退出和令牌保管；
- 浏览器只接收经过 AES-256-GCM 加密且带完整性保护的 HttpOnly、SameSite=Lax Cookie；生产 Cookie 同时启用 Secure，访问令牌不进入客户端组件、本地存储或页面源码；
- BFF 只从受保护会话读取访问令牌，并向 Spring Boot API 添加 `Authorization: Bearer`；不转发浏览器自带的授权头，也不接受用户名头；
- Spring Boot 使用 OAuth 2.0 Resource Server 校验 JWT 签名、签发者、受众、时间约束，并从可配置声明（默认 `preferred_username`）取得外部用户名；
- 该用户名必须与 `identity.user_accounts.username` 中状态为 `ACTIVE` 的记录精确匹配。未知或停用用户认证失败；外部组与角色声明不成为贯序业务权限；
- `guanseq.security.mode` 只有 `disabled`、`development`、`oidc` 三种值。`development` 才启用本地 Basic 用户；`oidc` 才启用 Bearer JWT；两者不并存；
- 状态检查端点继续匿名开放，其他后端端点全部需要认证；OpenAPI 以 Bearer JWT 描述正式契约，Basic 仅保留为非生产实现细节；
- 第一阶段不在浏览器会话中保存刷新令牌。访问令牌失效后重新进入授权码流程，身份提供者已有会话时通常无需再次输入凭据。后续只有在明确的会话时长需求和吊销机制齐备后，才评估刷新令牌轮换。

本决策不选择具体身份供应商，不自动同步用户、组织和角色，也不改变贯序内部工作区与权限数据所有权。

## 后果

### 正面

- 后端可以独立验证正式身份，BFF、网络代理或前端不能伪造内部用户名；
- 身份供应商可通过标准发现文档、授权端点和 JWK 集替换；
- 令牌不暴露给浏览器脚本，降低 XSS 后令牌直接泄露的风险；
- 外部认证与内部账号启停、工作区、角色和审计保持清晰边界；
- 本地开发适配器继续可用，但不会被误配置为正式认证方式。

### 代价与风险

- 新增 Spring Resource Server 与前端 OIDC 客户端依赖，并需要维护客户端密钥、会话加密密钥、回调地址、签发者、受众和 JWK 地址；
- 单个加密 Cookie 受浏览器大小限制，因此会话只保存必要令牌字段，并拒绝超限载荷；
- 不使用刷新令牌意味着访问令牌到期后需要重新跳转身份提供者；
- 外部用户名变更不会自动同步，管理员必须先维护贯序内部账号；
- 生产部署必须保证 HTTPS、准确的外部回调地址、时间同步和密钥轮换流程。

## 验证方式

- 成功指标：正式模式下 Basic 被拒绝；签发者、受众、签名或用户名无效的 JWT 被拒绝；有效 JWT 只能映射到启用的内部用户；登录临时状态和访问令牌均不可由浏览器脚本读取。
- 监控证据：后端身份链路集成测试、JWT 映射测试、OpenAPI 契约测试、前端会话加密与防篡改测试、lint、类型检查、全量自动化测试和生产构建全部通过；认证错误保留 `X-Request-Id`。
- 验收时间：首次身份提供者试点联调时完成真实签发者、回调、退出、令牌过期与账号停用验收。

## 退出条件与替换路径

若目标身份提供者无法提供标准 OIDC 授权码流程和可验证 JWT，或正式部署被要求采用受管网关的令牌交换模式，则创建新 ADR 取代本决策。替换时保留 `guanseq.security.mode`、BFF 令牌保管边界以及“外部身份只映射内部启用用户”的接口，优先更换协议适配器，不改写业务模块权限事实。
