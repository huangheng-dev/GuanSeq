# ADR-0001：模块化单体架构

- 状态：接受
- 日期：2026-08-14
- 决策人：GuanSeq 产品与工程团队
- 关联需求/问题：前端基线完成后，建设订单到交付的真实业务闭环
- 取代：无
- 被取代：无

## 背景与问题证据

GuanSeq 面向普通制造企业，销售、计划、采购、库存、生产、质量和成本之间存在大量强一致性关系。当前需要在保持业务事实一致的前提下，尽快完成第一条可以真实运行和审计的业务闭环。

## 决策驱动因素

- 制造业务关键事实需要可靠事务一致性。
- 第一条业务闭环需要较低的开发、测试和部署复杂度。
- 各业务域必须保持清晰的数据所有权和依赖方向。
- 架构需要支持单工厂起步并保留后续演进空间。

## 决策

当前批准的系统架构为：

```text
guanseq-web（Next.js）
    → REST / OpenAPI
guanseq-server（Spring Boot + Spring Modulith）
    → PostgreSQL + Flyway
```

`guanseq-server` 按业务事实划分模块。每个模块拥有自己的领域模型、应用用例、数据库表、迁移脚本和公开 API。跨模块协作只能通过公开 API 或已经批准的业务事件完成。

当前架构清单只包含上述已批准组件。新的技术组件必须在出现真实需求后单独建立 ADR，批准后再进入架构图和实施计划。

## 后果

### 正面

- 关键业务动作可以使用本地事务保持一致性。
- 初始部署单元少，开发和故障定位直接。
- 模块边界明确，为后续演进保留清晰接缝。
- 数据库迁移和 API 契约拥有统一事实来源。

### 代价与风险

- 必须持续运行模块边界测试，防止退化为无边界单体。
- 模块共享业务进程，需要通过代码边界和测试控制故障影响。
- 架构变化必须通过新 ADR，而不能在业务开发中顺手加入组件。

## 验证方式

- Spring Modulith 验证模块依赖无循环和越界访问。
- PostgreSQL 容器集成测试验证关键事务与约束。
- 第一条订单到交付闭环能够在该架构内完整运行。
- OpenAPI 契约能够驱动前端正式 API 适配器。

## 退出条件与替换路径

当现有架构无法满足已经测量的业务、性能、隔离或交付需求时，创建新的 ADR。新 ADR 必须以实际数据说明问题、迁移范围和回退方式，并明确取代本决策的具体部分。
