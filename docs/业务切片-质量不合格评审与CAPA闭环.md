# 业务切片：质量不合格评审与 CAPA 最小闭环

> 状态：已完成  
> 日期：2026-08-29  
> 正式路径：`/quality/nonconformance/records`、`/quality/nonconformance/reviews`、`/quality/nonconformance/actions`

## 1. 目标与事实边界

本切片把来料检验和完工检验已经判定的不合格数量转化为质量模块拥有的 NCR（不合格记录），形成“来源检验 → 评审 → 处置决定 → CAPA 计划与执行 → 有效性验证 → 关闭/重新处置”的责任闭环。

质量模块只拥有不合格评审、处置决定和纠正措施证据，不直接修改采购退货、生产返工、报废或库存余额。`RETURN_TO_SUPPLIER`、`REWORK`、`SCRAP`、`CONCESSION` 等处置类型是受控决定，不表示下游物理事务已执行；实际退货、返工、报废或库存移动仍必须由对应模块的正式单据完成。

首版只承接 `quality.inspections` 中的 `INCOMING` 与 `FINAL` 检验，不越界扫描 sales、procurement、production 或 warehouse 的内部表。销售退货质量判定等其他来源以后只能通过质量模块公开命令接入。

## 2. 对象、状态与动作

一个有不合格数量的检验对应一个 NCR，检验完成事务内自动创建；V59 对历史已完成且不合格数量大于零的检验做一次性回填。

```text
OPEN
  → REVIEWED
      → ACTION_REQUIRED → ACTION_IN_PROGRESS → VERIFICATION_PENDING
      → VERIFICATION_PENDING（评审认定无需 CAPA）
  → CLOSED（验证有效）

VERIFICATION_PENDING
  → CLOSED（有效）
  → ACTION_REQUIRED / REVIEWED（无效，返回重新计划或重新处置）

CLOSED
  → ACTION_REQUIRED / REVIEWED（有证据地重新打开）
```

- `REVIEW`：填写严重度、即时遏制、评审结论和是否需要 CAPA；`HIGH`、`CRITICAL` 强制需要 CAPA。
- `DISPOSE`：记录处置类型、决定、执行证据和责任人；需要 CAPA 时进入 `ACTION_REQUIRED`，否则直接等待有效性验证。
- `PLAN_ACTION`：记录根因、纠正措施、责任人和到期日。
- `COMPLETE_ACTION`：责任人提交完成证据，进入有效性验证。
- `VERIFY`：记录有效/无效及结论；有效则关闭，无效则返回重新计划或重新处置。
- `REOPEN`：已关闭记录发现后续失效时填写原因重新打开，原事件不可覆盖。

关闭是业务状态，不是物理删除；所有动作都校验 `expectedVersion` 并使用 `X-Request-Id` 幂等。

## 3. 权限、范围与责任

- `QUALITY_NONCONFORMANCE_READ`：质量检验员、质量经理、采购经理、生产经理和管理员读取当前工作区记录。
- `QUALITY_NONCONFORMANCE_REVIEW`：质量经理和管理员执行评审、处置和重新打开。
- `QUALITY_CORRECTIVE_ACTION_EXECUTE`：质量检验员、质量经理、采购经理、生产经理和管理员计划或完成 CAPA。
- `QUALITY_CORRECTIVE_ACTION_VERIFY`：质量经理和管理员验证有效性并关闭。
- 客户端不能指定租户或工作区；所有查询和动作同时注入当前租户、当前工作区边界。
- 责任人名称是计划时的业务快照，实际提交人、验证人继续使用认证用户 UUID、时间和请求编号记录。

首版不强制验证人与执行人必须是不同账号，以兼容单管理员的小型安装；页面和证据会明确展示两者，企业需要职责分离时由后续安装策略或权限配置增强。

## 4. 关键不变量与恢复

- 只有已完成、`rejected_quantity > 0` 的质量检验才能产生 NCR；一笔检验最多一个 NCR。
- NCR 的来源、物料、不合格数量和原始缺陷是检验快照，不允许前端修改。
- `HIGH`、`CRITICAL` 不允许跳过 CAPA。
- CAPA 到期日不能早于当前工作区业务日期；完成措施前不能验证。
- 验证无效不会覆盖原计划和完成事件，而是追加事件并返回可恢复状态。
- 版本冲突返回 `409`，状态/业务规则不满足返回 `422`，越权返回 `403`，跨工作区对象返回 `404`。
- 查询和查看详情不写事件；写动作记录动作、前后状态、操作者、原因、请求编号和结构化证据。

## 5. 页面与验收

- 三条产品路径复用同一正式后端事实，但分别以记录、评审队列和纠正措施工作视角打开。
- 列表使用服务端分页与状态、严重度、来源、到期风险和关键字筛选；详情展示来源检验、快照、当前责任、CAPA 和完整事件时间线。
- 页面覆盖加载、空数据、无权限、参数校验、接口失败、提交中、请求幂等和并发冲突，不回退为 Mock。
- 自动化必须覆盖自动建单/历史回填、工作区隔离、权限、正常 CAPA、无需 CAPA、验证无效回退、重新打开、幂等和版本冲突。

## 6. 验证结果

- 前端 lint、类型检查、54 个测试文件/151 项测试与 60 条应用路由生产构建通过。
- 后端以 PostgreSQL 18.4 验证 V1—V59 与 2 个本地可重复迁移；集成测试覆盖自动建档、权限、工作区隔离、幂等、并发、CAPA/无 CAPA、验证无效和重新打开。
- 生产镜像浏览器冒烟覆盖“来料部分不合格 → 自动建 NCR → 评审 → 处置 → 有效性验证 → 关闭”，并继续执行采购退货主流程。

## 7. 明确未完成

- 处置决定自动创建采购退货、生产返工、报废或库存事务；
- 销售退货、客诉、过程检验、设备或外部系统来源自动建 NCR；
- 附件、电子签名、8D、供应商门户、通知升级和可配置审批；
- 动态角色、强制职责分离、字段级权限和跨工作区质量看板。

这些能力只有在真实流程和责任边界确定后再建设，不因产品目录存在而提前引入新服务或基础设施。
