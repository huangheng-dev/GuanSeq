## 0. 设计立场（面向普通制造企业）

1. **版本快照，不就地改历史**：每次结算生成一条不可变记录；重算时新增一条版本号 +1 的快照，旧记录标记为 `SUPERSEDED`。审计、对账和往期报表永远能查到当时的数字。
2. **红字不自动改写利润，只打"受影响"标记**：红字发票、退款、反核销过账后，若该订单已有利润结算，把现行快照标记为 `IMPACTED`，台账显示"利润受后续单据影响，需要重算"。由财务人员在确认后一键重算，避免系统在用户不知情时偷偷改毛利数字，也避免部分退款导致频繁重算。
3. **重算后新快照口径自动对齐**：收入改为"蓝字发票含税净额 + 红字发票净额（负数）"；材料、人工、制造费用仍按实际领料、标准成本、工时与费率计算，并按**当前净发货量**分摊——价格折让类红字只减收入不减成本，退货类红字因仓库已收货会减少发货量从而同步减成本。
4. **重算原因必填**：至少 4 个字符，记入事件表，满足审计和税务对"为什么改利润"的可追溯要求。
5. **期间关账阻止重算**：重算新快照的业务日期必须落在开放期间；已经关账月份的利润不能被新版本覆盖（必须先重开期间）。
6. **不做自动期间结转、不做标准成本差异释放、不做多币种重估**：这些属于后续"总账与成本结转"切片。

## 1. 业务目标

让订单利润在红字发票/退款/反核销发生后可以被识别、冲销并按最新事实重新计算，同时保留完整版本链：

```text
红字发票/退款/反核销过账
  → 若该订单已有 SETTLED 利润快照
      → 标记为 IMPACTED（不删、不改金额）
      → 台账显示"需重算"徽标
  → 财务确认后点击"重算利润"
      → 校验期间开放、填写原因
      → 旧快照置为 SUPERSEDED
      → 按最新事实生成版本号 +1 的新 SETTLED 快照
      → 记录 RESETTLE 事件，关联旧快照 ID
```

## 2. 事实所有权与模块协作

- `finance` 模块拥有利润结算快照和版本链；其他模块不得直接写该表。
- 红字发票/退款/反核销（仍在 `finance` 模块内）过账成功后，调用 `OrderProfitApplicationService.markImpactedIfSettled(salesOrderId)`，把该订单的 SETTLED 快照置为 `IMPACTED`。
  - 这是模块内协作，不需要发跨模块事件，也不引入 Outbox。
  - 只打标记，不阻塞红字过账本身（红字是更基础的财务事实）。
- 仓库退货（销售退货入库）影响发货数量，属于仓储/销售模块事实，本切片只在重算时读取当前净发货量，不主动调用仓储接口。
- 会计期间守卫在重算新快照时校验业务日期。

## 3. 结算快照对象

### 3.1 数据结构（在现有表上扩展）

`finance.order_profit_settlements` 新增：

- `settlement_version INTEGER NOT NULL DEFAULT 1`：同一订单的第几次结算，首次为 1，重算一次 +1。
- `supersedes_id UUID NULL`：重算时指向被替代的上一版本快照 ID。
- `status VARCHAR(16) NOT NULL DEFAULT 'SETTLED'`：`SETTLED`（当前有效）、`SUPERSEDED`（已被新版本替代）、`IMPACTED`（SETTLED 但后续有红字/退款/反核销，等待重算）。
- `impact_reason VARCHAR(500) NULL`：被标记为 IMPACTED 的原因摘要（如"红字发票 CN-2026-0012 过账"）。
- 既有金额字段（revenue/material_cost/labor_cost/overhead_cost/processing_cost/total_cost/gross_profit/gross_margin）和 `cost_status`、`missing_items` 保持不变。

`finance.order_profit_events` 新增动作：

- `RESETTLE`：从旧版本生成新版本，details 含 `supersedesId`、`reason`、各金额。
- `MARK_IMPACTED`：红字/退款/反核销触发，details 含触发单据类型和编号。

### 3.2 状态机

```text
首次 settle:
  (无) ──settle──→ SETTLED

后续事实变更:
  SETTLED ──红字/退款/反核销过账──→ IMPACTED

重算:
  IMPACTED ──重算──→ SUPERSEDED  + 新建一条 SETTLED(version+1)
  SETTLED   ──重算──→ SUPERSEDED  + 新建一条 SETTLED(version+1)
                          （允许人工在无 IMPACTED 标记时也重算，用于补录成本后刷新）

被替代的快照:
  SUPERSEDED 为终态，不再变化
```

- 同一 `sales_order_id` 最多只有一条 `status IN ('SETTLED','IMPACTED')` 的快照（部分唯一索引）。
- `SUPERSEDED` 快照不进默认台账列表，但可通过"历史版本"入口查看。

### 3.3 核心规则

- **收入口径变更**：新快照收入 = 该订单所有蓝字发票未税净额之和 + 所有应收红字发票未税净额之和（红字为负数）；不再用 `shippedQuantity × unitPrice`，因为折让类红字不改变发货量。
- **成本口径不变**：材料成本 = 实际领退料净用量 × 标准成本；人工成本 = 已审核工时 × 工作中心人工费率；制造费用 = 标准工序分钟 × 制造费率。三者按"净发货量 / 合格入库量"分摊到发货行。
  - 退货类红字：若仓库已做销售退货入库，净发货量下降，成本自动按比例减少。
  - 折让类红字：净发货量不变，成本不减，只减收入——这正是折让的经济实质。
- **重算幂等**：以 `X-Request-Id` 幂等；重复提交返回同一新快照。
- **乐观锁**：旧快照 `@Version` 校验，并发重算返回 409。
- **重算原因**：≥4 字符，≤500 字符。
- **不可删除**：任何版本都不能物理删除；只能被新版本替代。

## 4. 权限

| 操作 | ADMIN | FINANCE_MANAGER | 其他角色 |
|------|:-----:|:---------------:|:--------:|
| 查看利润结算与历史版本 | ✅ | ✅ | ✅ |
| 首次结算 | ✅ | ✅ | ❌ 403 |
| 重算利润 | ✅ | ✅ | ❌ 403 |
| （无"删除结算"操作） | — | — | — |

重算不单独收紧到 ADMIN——普通制造企业财务经理月末重算利润是常规操作，但原因必填+审计+期间守卫已经构成足够控制。

## 5. API 与数据事实

### 5.1 OpenAPI（新增/扩展）

- `POST /api/v1/finance/order-profits/{salesOrderId}/settle`（已有，保持）：首次结算。
- `POST /api/v1/finance/order-profits/{salesOrderId}/resettle`：重算。
  - 请求体：`{ "reason": "string (4-500)", "settlementDate": "YYYY-MM-DD（可选，默认今天）", "expectedVersion": long（可选，乐观锁） }`
  - 响应：新结算记录（含 `settlementVersion`、`supersedesId`、`status=SETTLED`）。
  - 错误：403 无权限；404 订单无可重算快照；409 期间关账/乐观锁冲突/已有更新版本；422 原因不合规或订单未发货。
- `GET /api/v1/finance/order-profits/{salesOrderId}/history`：列出某订单所有版本（含 SUPERSEDED），按版本号倒序。
- 列表响应 `OrderProfit` schema 扩展：`settlementVersion`、`supersedesId`、`status`、`impactReason`。

### 5.2 Flyway V30 摘要

- `ALTER TABLE finance.order_profit_settlements ADD COLUMN settlement_version ...` 等 4 列。
- 回填：现有记录 `settlement_version=1, status='SETTLED'`。
- 删除旧的 `(tenant, sales_order_id)` 唯一约束，替换为部分唯一索引：`UNIQUE (tenant_organization_id, sales_order_id) WHERE status IN ('SETTLED','IMPACTED')`。
- 更新 CHECK 约束：`status IN ('SETTLED','SUPERSEDED','IMPACTED')`。
- 新增 `idx_order_profit_status` 供台账按状态筛选"需重算"。

### 5.3 前端

- 订单利润台账列表增加"状态"列：`SETTLED → 当前有效`、`IMPACTED → 需重算`（warn 色）、`SUPERSEDED` 默认不展示。
- 顶部指标卡增加"待重算订单"计数（IMPACTED 数量）。
- 每行在 SETTLED/IMPACTED 状态下显示"重算"按钮；IMPACTED 行按钮高亮并带 badge。
- 重算弹窗：显示当前收入/成本/毛利、填写原因、可选重算日期、提交；提交后刷新台账并 toast 提示新版本号。
- 结算详情抽屉增加"历史版本"区：列出该订单所有 SUPERSEDED 版本（版本号、结算时间、收入、毛利、被替代原因），可展开查看。

## 6. 失败与并发语义

- 无权限：`403`。
- 期间已关账：`409 PERIOD_CLOSED`（复用会计期间守卫，含 `X-Period-Label` 头）。
- 乐观锁冲突：`409`，提示"利润已被其他操作更新，请刷新后重试"。
- 订单无可重算快照：`404`。
- 原因缺失或 <4 字符：`422`。
- 订单未发货或净发货为 0：`422`（与首次结算一致）。
- 幂等：`X-Request-Id` 相同返回同一新快照。
- 并发红字 + 重算：红字先置 IMPACTED，重算读取最新事实生成快照；若重算先提交，红字后置 IMPACTED，下次仍可重算。

## 7. 明确不在本切片

- 利润快照的导出/打印（后续报表切片）。
- 标准成本差异释放、成本中心分摊、作业成本法（后续"成本结转"切片）。
- 多币种汇率重估、汇兑损益。
- 总账凭证自动生成（本期借贷平衡、损益结转）。
- 跨期利润调整（本期发现上期错误，通过红字+重开期间处理，不做单独的"以前年度损益调整"科目）。
- 自动重算（定时任务或事件驱动）——普通制造企业不需要，一键手动重算已经足够。

## 8. 验收证据

- Flyway 在一次性 PostgreSQL 18 容器中从空库迁移至 V30 成功；既有 V23/V26 利润数据回填 `settlement_version=1, status=SETTLED`。
- OpenAPI 契约测试覆盖新端点和扩展字段。
- PostgreSQL 集成测试覆盖：
  - 首次结算后状态为 SETTLED、版本 1。
  - 红字发票过账后该订单结算变为 IMPACTED，`impact_reason` 含红字单号。
  - 重算生成版本 2 SETTLED 快照，旧版本 SUPERSEDED 且 `supersedes_id` 指向旧 ID；收入已扣减红字金额。
  - 部分退款后重算，收入 = 原发票 − 红字 − 退款（退款不影响收入，只影响应收余额；本切片收入口径只含发票+红字，退款不重复扣减——此断言在测试中明确）。
  - 反核销红字后重算，收入恢复到反核销后状态。
  - 重算原因 <4 字符返回 422。
  - 重算日期在已关账月份返回 409 PERIOD_CLOSED。
  - 无权限角色重算返回 403。
  - 同一订单同一时间只能有一条 SETTLED/IMPACTED（部分唯一索引生效，并发重算不产生两条 SETTLED）。
  - `GET .../history` 返回版本倒序，首条为当前 SETTLED。
  - 幂等：相同 `X-Request-Id` 重算返回同一新快照。
- 前端：Zod 契约覆盖新状态；台账"待重算"计数、重算弹窗、历史版本抽屉均可见；`pnpm lint/typecheck/test/build` 全通过。
- 完整交付门禁：后端 `mvn verify`（Testcontainers）、前端 `pnpm check`。
