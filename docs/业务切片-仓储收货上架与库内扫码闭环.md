# 业务切片：仓储收货上架与库内扫码闭环

## 状态

- 状态：已完成（2026-08-27）
- 所属主线：采购与备料 → 仓储收货上架 → 生产与发运
- 业务事实所有者：`warehouse`
- 契约事实来源：`guanseq-server/src/main/resources/openapi/guanseq-api-v1.yaml`
- 数据库事实来源：Flyway 迁移

## 目标

把已经形成库存事实、位于收货区或待检区的合格库存，通过可审计的上架任务移动到同仓库的正式存储库位。移动端页面支持键盘输入、USB/蓝牙扫码枪输入和未来 PDA 调用，但扫码设备不成为业务事实来源。

## 业务边界

- 上游采购收货、完工入库和质量判定继续拥有各自业务事实；本切片不复制收货单或检验单。
- 上架源必须是 `AVAILABLE` 库存，源库位类型必须为 `RECEIVING` 或 `INSPECTION`，可用量必须大于零。
- 目标必须是同仓库、状态为 `ACTIVE`、类型为 `STORAGE` 的不同库位。
- 不实现跨仓调拨、波次、容器/LPN、相机识别、RFID、离线数据库或 Broker 直连。
- 库存仍以余额和不可变流水为唯一事实；上架完成产生源库位 `ISSUE` 和目标库位 `RECEIPT` 两条流水，来源统一为 `PUTAWAY_TASK`。

## 状态机

```text
OPEN ──完成上架──> COMPLETED ──冲回──> REVERSED
  └──取消──> CANCELLED
```

- `OPEN`：已创建、尚未过账；占用源库存的可上架额度，避免重复建单。
- `COMPLETED`：两端库存和两条流水已在同一事务内过账。
- `CANCELLED`：仅开放任务可取消，原因至少 4 个字符，不产生库存流水。
- `REVERSED`：仅已完成任务可冲回，产生方向相反的两条补偿流水；原流水不删除、不修改。

## 权限与责任

- 可执行角色：`WAREHOUSE_MANAGER`、`INVENTORY_CONTROLLER`、`ADMIN`。
- 后端授权是唯一可信边界；前端仅用于操作引导。
- 每个动作记录租户、工作区、操作者、时间、请求编号、动作前后状态和原因。
- 创建与各状态动作均使用 `X-Request-Id` 幂等；任务与库存余额使用版本检查，并在过账时锁定余额。

## 扫码契约

- 源库存标签：`STOCK:<库存余额 UUID>`。
- 目标库位：支持直接输入库位编码或 `LOC:<库位编码>`。
- 只做完整精确匹配，不做模糊猜测；未知、跨租户、停用或类型不符的条码明确失败。
- 页面断网时不提交业务事实；恢复网络后由用户确认并重试，服务端幂等保证不会重复过账。

## 验收条件

1. 合法源库存与目标库位可通过扫码精确解析并创建开放任务。
2. 同一源库存的开放任务总量不能超过其当前可用量。
3. 完成上架后源库存减少、目标库存增加，数量守恒，并生成两条可追溯流水。

4. 重复请求不会重复建单或重复过账；过期版本返回冲突。
5. 开放任务可取消；已完成任务只能以补偿流水冲回。
6. 无权限、跨租户、库位类型错误、质量状态错误、库存不足和并发冲突均被后端拒绝。
7. 正式页面覆盖加载、空数据、无权限、校验失败、接口失败、离线和并发冲突等适用状态。
8. 自动化测试、真实 PostgreSQL 迁移与浏览器主路径验收全部通过后，状态才可改为“已完成”。
