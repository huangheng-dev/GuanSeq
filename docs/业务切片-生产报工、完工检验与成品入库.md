# 业务切片：生产报工、完工检验与成品入库

## 目标

把已开工生产订单推进到可审计的完工事实：车间提交报工，质量模块独立判定，生产模块按判定结算，仓库模块只接收合格数量并形成库存余额与不可变流水。该切片不以直接修改生产订单完工数量代替车间、质量和库存证据。

## 业务对象与所有权

| 对象 | 所有模块 | 说明 |
|---|---|---|
| 生产订单、生产报工 | 生产 | 管理可报数量、在检数量、合格完工数量、报工人、班次和结算状态 |
| 完工检验 | 质量 | 保存送检数量、合格/不合格数量、检验员、缺陷、结论和不可覆盖的判定时间 |
| 成品库存余额、库存流水 | 仓库 | 按仓库、库位、物料、批次增加合格库存并保留来源证据 |

生产模块通过 `FinalInspectionProvider` 创建和读取质量事实，通过 `FinishedGoodsReceiptService` 请求成品入库；不得直接查询或修改质量、仓库模块的数据表。质量与仓库模块也不反向修改生产订单。

## 状态与规则

生产报工状态：

```text
PENDING_INSPECTION
  → READY_FOR_RECEIPT → RECEIVED
  → READY_TO_CLOSE   → CLOSED
```

- 只有 `IN_PROGRESS` 的生产订单可以报工。
- `可报数量 = 计划数量 - 已完工数量 - 在检报工数量`，提交报工时以生产订单版本号校验并发修改。
- 每笔生产报工自动生成一笔完工检验；检验前不增加生产完工数量和库存。
- 质量判定必须满足“合格数量 + 不合格数量 = 送检数量”；存在不合格数量时缺陷说明必填。
- 完工检验一经完成不得静默覆盖。
- 仅合格数量允许成品入库；仓库与库位必须有效且属于同一仓库，生产批次必填。
- 全部不合格的报工不产生库存流水，但仍需显式结算关闭并释放在检数量。
- 合格数量结算后增加生产订单完工数量；只有已完工数量达到计划数量且不存在在检报工时，生产订单才自动完成。
- 报工、检验判定、结算和库存入账均使用请求编号保证幂等，并保留责任人、时间、来源和审计事件。

## 数据与 API

Flyway：

- `V17__create_production_reporting_quality_receipt.sql`

主要接口：

- `GET/POST /api/v1/production/work-reports`
- `GET /api/v1/production/work-reports/{id}`
- `POST /api/v1/production/work-reports/{id}/settle`
- `GET /api/v1/quality/final-inspections`
- `GET /api/v1/quality/final-inspections/{id}`
- `POST /api/v1/quality/final-inspections/{id}/complete`

数据库结构以 Flyway 为事实来源，HTTP 契约以 `guanseq-api-v1.yaml` 为事实来源。

## 前端验收

- `/production/reporting/reports` 展示真实生产报工，支持搜索、状态筛选、勾选导出、分页、提交报工、查看证据和检验后结算。
- `/quality/final` 展示真实完工检验，支持搜索、状态筛选、勾选导出、分页、数量判定、缺陷记录和详情追溯。
- 报工页可跳转生产订单与完工检验；检验页可返回来源报工。
- 成品入库结算使用后端返回的真实仓库与库位引用，不使用前端硬编码标识。
- 页面只通过 `src/services` 和 BFF Route Handler 访问后端，所有后端响应均经过运行时契约校验。

## 已验证场景

- 正常开工、提交报工、部分合格/部分不合格检验、合格品入库与生产订单数量回写。
- 重复结算请求不会重复增加库存或生成第二笔来源流水。
- 直接对生产订单执行 `COMPLETE` 被拒绝，完工只能由报工链路形成。
- 版本冲突、数量越界、检验数量不守恒、缺陷说明缺失和无效仓库库位均由后端拒绝。

## 未完成边界

- 当前报工位于生产订单层级，车间工单、工序级派工、工序报工和在制品流转尚未接入。
- 生产领料、退料、补料、工序检验、不合格评审、返工返修和报废处置尚未接入。
- 成品入库已形成库存事实，但独立的仓储收货/上架任务页面尚未建设。
- 设备数据采集、条码扫码和自动报工不在本切片范围。
